# Problem

Search exposes CLSP voice retrieval rather than a model-selectable semantic transcript provider. Name matching removes names from the content query. Model preparation, automatic indexing, and readiness feedback need a common lifecycle.

# Implemented solution

Recorded the accepted architecture in [the Semantic Search design](../design/2026-10-06-semantic-search.md). Added reproducible Granite conversion and native validation scripts under `apps/worker-search/scripts/`. Prepared both model sizes with source packages, compiled models, tokenizers, Apache license, model cards, checksums, and synthetic validation inputs in ignored `tmp/semantic-search-2026-10-06/granite-{97m,311m}-v1/`. Both packages are published on Hugging Face with `v1` release tags. App integration now includes the Local Search catalog and form, model-specific artifacts and projection, managed indexing, complete-query ranking, General and Data settings, and loading feedback inside a native search field.

# Reasoning

Reuse the existing local model manager, managed tasks, and shared database. Keep the complete query and use confirmed speaker associations only for a bounded ranking bonus. Keep each model's vector space and source revisions distinct.

# Technical debt

The initial conversion used fixed 512-token inputs and FP32 computation because automatic FP16 conversion overflowed the attention mask. The validated mixed-FP16 replacement now uses selective FP32 operations with 128-token query and 512-token passage functions; see [embedding optimization](2026-10-06-embedding-optimization.md). Long passages are split before embedding, and queries longer than 512 tokens report an error. Dormant CLSP worker adapters and old configuration fields remain for experiment compatibility; the app routes Local Search to semantic retrieval and no longer offers Voice or Fusion. A separate cleanup can move the experimental adapters out of the app after their fixtures have an independent harness. Exact cosine retrieval scans one meeting artifact at a time, bounding memory by meeting; large-library latency and recording contention still need measurement before choosing a different vector projection.

# Rebuild interaction analysis

The user's real-library screenshots exposed limits that the two-meeting preview did not reveal: rebuild preparation has no visible progress, each meeting becomes a separate task, and completed history can hide active work. Source analysis confirms that Data only shows passage callbacks, discovery retains the previous status, task records require one meeting, and the chronological task page preserves its existing viewport. Reuse also produces a main-actor progress callback for every window, while every completed indexing task requests another freshness scan. These are concrete sources of avoidable work; the reported severe interaction delay still requires profiling before assigning a single cause. Inference already runs on a separate actor.

Recorded a proposed replacement in [Search index task behavior](../design/2026-10-06-search-index-tasks.md): one durable batch task, immediate phase feedback, aggregate and current-meeting progress, bounded UI updates, incremental coalescing, active tasks independent of history pagination, checkpointed recovery, and a replacement index generation that preserves search availability. This is analysis only; no production fix or new validation is claimed. The retained technical debt is the meeting-only task model and fragmented progress lifecycle; remedy them together rather than hiding individual tasks cosmetically. Concurrent app task-journal conflicts observed during startup measurement are a separate confirmed issue in that measurement run; explicit scheduler ownership is included in the proposal. No private meeting content was copied into the proposal.

The proposal now includes the user's universal task contract: all task types expose status, actual start, end, elapsed duration, and active duration, with queued/created timestamps and preserved attempt history. Started tasks sort by actual start time; never-started queued tasks retain explicit queue ordering rather than invented start timestamps. Existing managed tasks lack start/interval fields, voice jobs lack both start and end, and history indexes use creation time. Migration must retain unknown historical timing explicitly and update indexed pagination alongside display order. This requirement remains proposed; no task schema or UI implementation changed.
