title: Canonical Gday users with standard shared identity
status: implemented
---

Problem: MCP and desktop clients need interoperable OAuth/OIDC login; user management must remain authoritative in GdayMeetings.

Implemented solution: Better Auth 1.7.5 with its maintained OAuth Provider 1.7.5 plugin supplies discovery, public dynamic registration, authorization/consent, S256 PKCE, asymmetric ID tokens/JWKS, refresh rotation and revocation. The default issuer is SERVER_URL/api/auth. Resource audiences separate mcp:read at /mcp from meetings:read/meetings:write at /api/platform. Canonical Payload password login creates a stable-ID shadow solely for library sessions and grants; every browser and API authentication rechecks the Payload account. Disabled/deleted accounts cannot authenticate, and old identities cannot transfer grants when an email is reassigned. Public signup and independent shadow profile/password management are disabled. Admin/member roles restrict user management, with Payload and Gday sharing login sessions. Optional generic upstream OIDC is explicit account linking only, with implicit linking and provisioning disabled.

Reasoning: Replaced the unpublished bespoke OAuth draft with maintained protocol implementation. OAuth clients remain portable; application code implements canonical user lookup and resource authorization through a narrow identity adapter. Existing accounts retain their former administrator access via reviewed Payload migrations; new accounts default to member. The workspace is shared, not tenant-isolated.

Validation: Canonical lifecycle regression passes using both SQLite and isolated PostgreSQL17 production migrations: wrong password, disabled account, blocked signup, delete/recreate same email, and stale-session rejection. The parent integration suite covers actual SDK MCP authorization, PKCE and token scope/audience boundaries. Package versions verified against npm registry; implementation verified against official Better Auth OAuth Provider, generic OAuth, SQLite adapter and plugin documentation. Next authorization pages/API have no-store, frame-denial and no-referrer headers; request bodies are bounded to 64KiB even without Content-Length.

Technical debt: Better Auth's official additive schema migrator runs on first identity initialization rather than versioned application SQL. SQLite keeps auth.db in DATA_DIR; Postgres uses gday_auth_* tables alongside Payload. Start one replica for upgrades and back up both stores; future multi-replica deployment should run identity migration as a dedicated release job. JWT access tokens live five minutes and cannot be individually revoked by the provider; refresh revocation stops renewal, while session sign-out (for session-bound tokens) and canonical disable/delete immediately deny access. Future per-grant immediate access revocation requires supported provider functionality or a documented resource-server revocation design. External upstream integration uses the maintained provider and explicit-link UI but has no live external tenant fixture; validate tenant discovery/callback configuration before enabling it. No independent identity directory or email-based account auto-linking is introduced.

Notes: SQLite default and PostgreSQL support tested with separate synthetic databases. No production credentials or recordings copied. Official sources: https://better-auth.com/docs/plugins/oauth-provider, https://better-auth.com/docs/plugins/generic-oauth, https://better-auth.com/docs/adapters/sqlite, https://better-auth.com/docs/concepts/plugins.
